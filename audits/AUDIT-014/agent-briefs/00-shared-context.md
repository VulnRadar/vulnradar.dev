## FINDING SCHEMA (from the product owner's brief, follow it exactly)

One JSON object per finding, all keys present:

- `id` — readable `<scope>-NN` using the prefix in your task prompt.
- `title` — one specific sentence. What is wrong, not what area it is in.
- `section` — integer: 13, 14, 15, or 18. The section it truly belongs to.
- `type` — one of: bug, security, ssrf, ux, mobile, design, qol, removal, drift,
  perf, test, deps, db, deploy, docs, config, cleanup, seo, gap,
  opportunity
- `severity`— critical | high | medium | low | info
- `effort` — small | medium | large
- `category`— short grouping label. For `file: null`, this carries the scope.
- `file` — repo-relative path or null
- `line` — integer or null
- `description` — what the code/doc/config actually does, with file:line per hop.
- `impact` — what goes wrong for a user, an operator, or the business. Concrete.
- `recommendation` — the specific fix: file, function, change.

## SEVERITY CALIBRATION

- `critical` — a fresh self-host is impossible or silently broken, a secret is
  exposed, or a deploy path destroys data.
- `high` — a documented workflow does not work as written, a deploy step can fail
  silently, a hardcoded value breaks any non-default deployment, or a core flow is
  unusable by keyboard or screen reader.
- `medium` — real but bounded: degrades, or needs an unusual precondition.
- `low` — minor, cosmetic, or theoretical with a working mitigation.
- `info` — worth knowing, no action required. Use this for negative results too:
  recording what you verified as correct saves the next audit the work.

Do not inflate. A doc typo is `low`. A doc that tells an operator to run a command
that does not exist is `high`.
