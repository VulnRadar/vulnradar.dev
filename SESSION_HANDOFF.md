## Pages to manually test before trusting the CSP rewrite

The single highest-risk change this session was replacing `'unsafe-inline' 'unsafe-eval'` in script-src with a nonce + `'strict-dynamic'`, and switching COEP from `unsafe-none` to `credentialless`. This was grounded in a real audit of every third-party integration (Turnstile is `next/script`, auto-nonced by Next.js; BrowserBase is a plain iframe governed by `frame-src`, unaffected; Stripe.js is injected by our own nonce'd bundle, which is exactly what `'strict-dynamic'` is for) — but "grounded in code reading" is not the same as "confirmed in a real browser." Load the app and check, in this order:

1. **`/signup`** — does the Cloudflare Turnstile widget render and let you complete signup? This is the single most important check; Turnstile gates every new account.
2. **`/browser/[id]`** (open a live browser session from a scan result's "View page" button) — does the BrowserBase live-view iframe load and let you interact with it?
3. **Checkout** (if `BILLING_ENABLED`) — does the Stripe Elements payment form render and let you complete a test-mode charge?
4. **`/contact`** — Turnstile again, same widget, different page.
5. **Any page** — open devtools console, look for CSP violation errors mentioning `script-src` (real breakage) or `require-trusted-types-for` (report-only, informational — expected to log warnings if anything trips it, does not block anything).
6. **Cloudflare Analytics** (if you have dashboard access) — confirm events are still arriving after a day or two live.

If any of 1-3 are actually broken, the likely culprit is something the code-reading audit missed (a dynamically-injected script from one of those SDKs that isn't covered by `'strict-dynamic'` propagation the way expected) — check the console error message, it will name the exact blocked resource.

### Notification banner bug (3 real, separate wiring gaps, not one)

Root cause was not what it looked like from the bug report ("banner option doesn't work") — there was never a missing toggle; the banner/modal/toast renderer already existed and was already mounted. Three actual, independent bugs in the data path from "admin saves" to "user sees it":

1. **Timezone double-conversion on `starts_at`/`ends_at`** in `notifications-manager.tsx` — a `datetime-local` value was built from a UTC ISO string with no conversion, then re-interpreted as local time again on save. For any admin not in UTC, this could push `starts_at` into the future, so `WHERE starts_at <= now` silently excluded a just-created notification. This was the actual "banner never shows up" bug.
2. **`path_pattern` ("Page Filter") was a dead column** — written and displayed, never read by anything server-side or client-side, so a notification scoped to one page showed everywhere. Added `lib/notifications/match-path.ts` (glob matcher) and wired it into both the bell and the banner/modal/toast renderer.
3. **Audience targeting silently broken for banner/modal/toast** — the fetch powering `SiteNotificationsWrapper` sent no query params, and the API defaults `authenticated`/`staff` targeting to `false` when absent, so only the default "all" audience ever actually displayed.

Also rebuilt the create/edit modal's UI to match `system-settings-manager.tsx`'s established admin design language (boxed sections, `divide-y` field rows, shadcn `Select`), same field set. Added `tests/lib/notifications/match-path.test.ts`, which didn't exist before.
